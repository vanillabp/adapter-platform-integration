### A workflow aggregate which did not change is not written

After every `@WorkflowTask` method the core calls `AggregatePersistenceAware#save`, whether the method changed the
aggregate or not. That stays. The MongoDB persistence of the platform leaves out the write when the aggregate did
not change since `loadById` loaded it in the same transaction. That is Spring Data MongoDB behind
`SpringDataUtilBasedAggregatePersistenceSupport`, and MongoDB Panache as a repository and as an active record. JPA
stays as it is, because Hibernate checks itself whether an entity is dirty.

Why: MongoDB has no such check. A repository replaces the whole document on every save. `@Version` raises the version
and an auditing field like `@LastModifiedDate` changes on every save. So in a parallel multi-instance all iterations
but one failed inside the MongoDB transaction, although none of them changed anything. The BPMS retried them, and
when the attempts were used up it raised an incident. Measured on 2026-10-20 against `mongo:8.2` with a replica set
and four iterations: on Spring Boot with `@Version`, three of four failed with a write conflict (error code 112).
Without `@Version` the server took the unchanged document as a write which changes nothing, and nothing failed.

How the comparison works: at `loadById` the persistence keeps the document which the converter of the framework
would write for the object. That is the `MongoConverter` of Spring Data and the codec of the collection on Panache.
Right before `save` writes, it builds that document again and compares the two. Both are built before the write. So
neither the version attribute nor an auditing field counts as a change, because only the write sets them. A reference
to a document of another collection (`@DBRef`, `@DocumentReference`) is written as the reference. So a change in the
referenced document is no change, and a reference which points elsewhere, is added or is removed is one. A lazy
reference is written from its proxy without loading it. An object mapped as a sub-document is part of the document.

The document is kept per object, by identity, as a resource of the running transaction: a Spring transaction
resource, and a resource of the JTA transaction on Quarkus. So it never reaches another delivery, and it is gone when
the transaction ends. Without a transaction nothing is kept, and every save writes.

Why this does not touch decision 14: the core still saves after every handler, and a conflict of a handler which
really writes is still reported and passed on unchanged, not retried. What goes away is a conflict which no
application code caused. It also takes away a side effect: with `@Version`, a handler which only read the aggregate
used to fail when somebody else changed the aggregate meanwhile. It does not any more, as on JPA. A handler which
writes nothing has nothing to protect, so there is no switch to bring the old behaviour back.

Why the comparison lives in the persistence and not in the core: only the persistence knows what it would write. The
core would need a deep copy and an equality of arbitrary objects, and it could not tell a reference from an embedded
object, or a version attribute from a field the application changed. An `AggregatePersistenceAware` of the
application decides by itself whether it writes. Its javadoc says it may leave out an unchanged aggregate.

MongoDB reports a second writer inside a transaction as a write conflict, also without a version attribute. Spring
translates it into a `DataIntegrityViolationException`, not into an optimistic locking failure. So
`AggregateWrite#causedByOptimisticLocking` also counts a `com.mongodb.MongoException` with error code 112, matched by
name and code, so the core stays free of the driver. Then the guiding message of decision 14 appears for MongoDB as
well. Before, it did not, on either platform.

Limits: the comparison costs one more conversion of the aggregate per load and per save. Two maps which hold the same
entries in another order count as equal on Spring Data and as different on Panache, which compares the bytes of the
encoded document. Different means one write too many, never a write too few. A value which a custom converter of the
application writes as a mutable object may hide a change made in place.
