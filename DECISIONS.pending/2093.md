# Addendum to decision 135: an attempt which started before the deadline does not end the wait

Proposed by story 2093, 2026-11-06.

**What was wrong.** Decision 135 says that the store blocks an entry at the deadline its adapter
named, and that this block is the net for a window which ends after the deadline. The store compared
the deadline with its own clock, read when the answer of the adapter arrived. So the net also fired
for an attempt which started in time. The Camunda 7 family reads the clock in the adapter, finds the
deadline ahead, and answers "not yet". A few milliseconds later the store read a clock which was
past the deadline, and it blocked the entry.

That has two effects. The operator gets the wrong text: the last answer says "It is tried again until
its message time-to-live is over", and the text of the adapter, which says what to check and which key
to raise, is lost. And the last attempt which `nextWaitForASubscription` plans for the end of the
time-to-live does not happen, so a workflow which reaches the catch event in the rest of the
time-to-live finds its message blocked. The first effect was seen on 2026-11-06 in run 42223182259
of cibseven-adapter. The second follows from the code. Nobody has seen it happen.

**The rule now.** The store compares the deadline with the moment the attempt STARTED.
`PhaseTwoOutboxProperties#hasWaitedLongEnough` is still the one rule, and all three stores of this
repository ask it. An attempt which started before the deadline gets one more attempt, with the
window it named. An attempt which started at the deadline or later has seen it. If the adapter still
says "not yet" then, the store blocks the entry, as before.

**What this means for an adapter.** An adapter which ends the wait itself now always gets to say what
ran out. The window `Camunda7ProcessService` names is never longer than what is left, so the next
attempt starts at the deadline, and the wait is at most one attempt longer than it was. The same
applies to `wait-for-visibility-at-most`, which uses the same rule.

**Why not in the adapter.** An adapter cannot close this. It answers before the store reads the
clock, whatever margin it adds, and a pause of the JVM between the two is longer than any margin
worth having.

**Where it is referenced.** Comments in `JdbcPhaseTwoOutboxDispatcher#waitForTheReadModel` and both
`MongoPhaseTwoOutboxDispatcher#waitForTheReadModel`, which cite decision 135; the javadoc of
`PhaseTwoRetryLater`; `migration-adapter/ADAPTER-AUTHORS.md` near "End the wait yourself". The tests
are `WaitingForAReadModelUsesNoAttemptsTest`, `AMongoBlockedEntryKeepsItsReasonTest` and
`MongoBlockedEntryKeepsItsReasonTest`.
