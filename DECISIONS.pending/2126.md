### On Spring Boot, a section of the vanillabp tree written as {} keeps the keys below it

Proposed by story 2126.

**Why.** Spring Boot reads the empty map of a YAML file as a property with an empty value.
`vanillabp.adapters.saas: {}` becomes `vanillabp.adapters.saas=`. When Spring Boot binds an object,
it looks for a value at the object's own name first, in every property source. It found the empty
value and did not read the keys below the name. So `type`, `deployment-failure` and a module's
`resources-location` from the command line, an environment variable or a second YAML document were
lost. The startup said nothing, which breaks the rule that a key VanillaBP does not read ends the
startup. The same happened in every overlay class of an adapter.

**What.** The platform fixes it once, for everybody who binds under `vanillabp`. `EmptySections`
gives a section the bind restriction `NO_DIRECT_PROPERTY` where keys exist below it. Then Spring
Boot reads the keys and skips the empty value. Where nothing exists below the name, the binding stays
as it was, so a section of nothing but `{}` still configures its id. The auto-configuration of the
platform registers the rule as a `ConfigurationPropertiesBindHandlerAdvisor`, and Spring Boot applies
it to every `@ConfigurationProperties` class. A `Binder` which binds the tree directly passes
`EmptySections.bindHandler()`.

**Which types.** Every type whose class name starts with `io.vanillabp.`, bound below the name
`vanillabp`, except enums. That covers the core model and the overlay classes of the adapters and of
the extensions, because they live in packages below `io.vanillabp` as well. The rule relies on one
promise: a VanillaBP type below `vanillabp` is always a section. A single value is a JDK type or an
enum, never a class of VanillaBP. A class which is converted from a single text would lose its value
under this rule.

**Rejected.** A restriction on every binding of the application: it would change how other
libraries bind. A list of the core types only: every adapter would need its own advisor for its
overlay, as the Camunda 7 adapter had one, and a new adapter would repeat the bug until somebody
noticed.

**Quarkus.** Not touched, and it needs nothing. The YAML source of SmallRye Config turns `{}` into
no property at all, not into a property with an empty value. SmallRye finds the keys of a map by
their names. So the keys of the id from another source arrive, whichever source is stronger. That
holds for system properties, for a profile and for an environment variable. The check for unknown
keys still finds a typo below the empty section. Quarkus has the other half of the problem: a
section of nothing but `{}` gives no name, so its id is lost. The wiki page `Quarkus-integration`
describes that limit.

**Tests.** `AnEmptySectionKeepsTheKeysTest` holds the cause, the binding of
`AdapterBeanRegistrarSupport`, the bind handler at adapter level, at workflow-module level and for
the whole tree, a section of nothing but `{}`, and a booted application with the core properties and
an overlay class. On Quarkus, `QuarkusEmptySectionKeepsTheKeysTest` binds the platform's config
mapping with a `{}` section and the keys in another source, in both orders, and holds the typo
check and the lost id of a section of nothing but `{}`.

**Where it is cited.**

- `spring-boot-integration/README.md`, section "Configuration binding"
- `migration-adapter/ADAPTER-AUTHORS.md`, section "Spring Boot"
- javadoc of `EmptySections`, `AdapterBeanRegistrarSupport#forEachConfiguredAdapterId` and
  `SpringBootMigrationAdapterAutoConfiguration#vanillaBpEmptySectionsKeepTheirKeys` describe the
  rule without citing the decision
