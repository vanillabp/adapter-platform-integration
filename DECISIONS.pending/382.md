# The gruelbox store leaves the platform, and what stays is the bridge and one refusal

Entry 75 said that gruelbox stays available inside this repository as an opt-in, behind
`vanillabp.outbox.gruelbox.enabled`, and that nothing in the platform depends on it any more. The
second half held. The first half is what this entry changes: the store is out, with its tests and its
library, and it lives in `vanillabp/gruelbox-phase-two-outbox`.

## Why the opt-in was not enough

A switch in the platform is a second decision. An application had to have the library AND set the
key, and the platform then had to say something sensible about every combination of the two. It also
kept paying for the library everybody carries: `com.gruelbox:transactionoutbox-core` and
`-spring` were `optional`, so no application inherited them, but this repository still compiled
against them, tested against them and answered for them.

What the move costs an application is one dependency, and its configuration stays as it is: the
section is still `vanillabp.outbox.gruelbox.*` and the table is still `TXNO_OUTBOX`.

## What stays in this repository

**The bridge.** `JdbcPhaseTwoOutboxAutoConfiguration` still counts what `TXNO_OUTBOX` holds
undispatched and warns about it. An application coming from that store needs the message exactly now,
when the code which read that table is gone. It names the artifact to add instead of a key, and it
carries the table name as a literal, because the class which declared that constant is in the other
repository. The name belongs to the library anyway: gruelbox defaults to it and its migration creates
no other.

**One refusal.** `GruelboxMissingAutoConfiguration` ends the boot of an application which sets
`vanillabp.outbox.gruelbox.enabled` while no gruelbox store is on the classpath. Without it such an
application would write its phase-two entries into another table than the one it still has work
waiting in, and nothing would say so. The condition reads the KEY rather than its value, so a value
Spring cannot read as a boolean is answered too; `false` is the one value which stays silent, because
an application writing it asked for the other store. The class condition names
`com.gruelbox.transactionoutbox.TransactionOutbox`, a class of the library, so this repository points
at no artifact of ours for a decision at startup.

**The key in the metadata.** `vanillabp.outbox.gruelbox.enabled` is described in
`META-INF/additional-spring-configuration-metadata.json` although nothing here binds it. A
development environment should still propose it and say where the store lives.
`EveryPropertyIsOfferedByTheIdeTest` names it as the one key described for another artifact.

**The Quarkus refusal.** It was there before and it stays, with one sentence added: the store is not
just absent on Quarkus, it is not part of VanillaBP at all.

## How the two stores take turns now

There is one bean name for the outbox of a relational aggregate, `vanillaBpJdbcPhaseTwoOutbox`. The
store of the other repository registers its outbox under that name and declares its
auto-configuration `before` this one, and this one carries `@ConditionalOnMissingBean` on that name.
So the dependency is the whole wiring, which is how `hazelcast-shared-election-cache` replaces the
in-memory election cache, and `SpringPhaseTwoOutboxResolver` knows one JPA default name instead of
two.

## What it cost beyond the move

Two dependencies which nobody had asked for came in through gruelbox and had to be asked for
explicitly once it was gone: `jackson-databind` in test scope, which the tests reading the
configuration metadata parse with, and `jackson-annotations` as `provided`, which javadoc needs to
read the annotations of Spring Boot's health classes. Both were invisible while a third party
dragged them in, which is one more argument for the move.

## What is still open

The wiki keeps one paragraph about the store, and this entry does not say which page it stands on.
Nothing in the platform cites that paragraph.
