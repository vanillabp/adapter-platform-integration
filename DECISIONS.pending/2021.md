### A refusal of phase one stands only where nothing of the workflow waits in the outbox

Phase one asks the BPMS, and an embedded engine answers from the caller's transaction (decision 3).
That answer is about the BPMS as it is now. An operation of the same workflow which is still in the
outbox has not reached the BPMS yet. So the answer can be about a state which is going to change.

The case which showed it: an application completes a user task and then correlates the message the
workflow waits for after that task. The two calls come one after the other, in one transaction or in
two. On Camunda 7, Operaton and CIB seven, phase one of the correlation asked the engine whether a
subscription waits. None did, because the completion runs only after the commit. So the correlation
failed, although the application had done nothing wrong. The blueprint `module-bpms-migration` waited
200 ms before each step to get around it.

What holds now: when phase one of an operation on a workflow refuses, the core asks the outbox whether
an entry of that workflow still waits (`PhaseTwoOutbox#hasPendingCallsOf`). "That workflow" means the
same workflow module, BPMN process and aggregate id. "Waits" means any entry which is not DONE, also
one which a dispatch is working on right now, and one which the running transaction wrote. If the
answer is yes, the core plans the operation anyway, and phase two decides. Phase two runs after the
waiting entry, because the stores VanillaBP ships dispatch one workflow's entries in the order they
were written (decision 100). If the answer is no, the refusal stands, and it is still thrown where the
application made the call.

The refusal stays as it was in these cases:

- A store which cannot say. The default of the new method answers "cannot say", so a store written
  outside VanillaBP behaves as before. The gruelbox store is one of them, and that is right for it:
  it does not keep the order, so phase two of the correlation could run before the completion and
  meet the same state.
- A store whose answer fails. The refusal is thrown, and the failure is attached to it as a
  suppressed exception.
- An operation the adapter does not support (`PhaseOperationNotSupported`). That answer does not
  depend on the state of the workflow, so the outbox is not asked.

**Why the core asks only after a refusal.** Asking first would cost a query on every operation, and
almost every phase one says yes. Asking after the refusal costs nothing where phase one agrees.

**Why the core does not tell the adapter.** The adapter could get a flag "something waits" and decide
on its own. Then every adapter would have to learn it, and the ones which do not would keep failing.
The question whether the BPMS state is final belongs to the outbox, and the outbox belongs to the
core.

**What it costs.** Where the refusal was right, it now arrives later. A correlation of a message which
nothing will ever wait for, planned while an entry of the same workflow waits, is no longer an
exception at the call. Phase two of the adapter meets no subscription and says so in its log. That is
the same answer an at-least-once repeat gets, so the adapters do not have to change for it. Their
message should not call it a repeated delivery any more, though.

`ARefusalWaitsForTheOutboxOfItsWorkflowTest` holds the rule in the core.
`ACorrelationRightAfterACompletionTest` holds it on Spring Boot and on Quarkus, with the JDBC store.
The `MongoOutboxDispatchTest` of both platforms holds the answer of the MongoDB stores.
