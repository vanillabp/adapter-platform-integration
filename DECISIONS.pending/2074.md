### The one runtime call to an extension is synchronous, isolated and has no outbox

Proposed by story 2074.

**Why.** An adapter refuses a call on a workflow which is suspended in its BPMS. Since story 2070, the
application gets a `WorkflowSuspendedException` in phase one, and the outbox entry waits in phase two.
Only the adapter sees this. An extension does not, and the Business Cockpit on Camunda 8 found a
suspension only with its hourly check, up to an hour late. Every other call from the core to an
extension belongs to the start or the end of the application. This is the first one while workflows
run, so its rules are written down once, here.

**What holds.**

- The adapter reports through a collaborator, `SuspendedWorkflowReporter` in `AdapterCollaborators`. It
  is never empty. A set built without it gets `SuspendedWorkflowReporter.NOBODY_LISTENS`, which drops
  every report, and nothing warns. An adapter of a BPMS which cannot suspend a workflow has nothing to
  report, and an adapter built before the reporter existed still builds. On Quarkus,
  `AdapterCollaboratorsSupport.collaborators` has a second variant with the reporter as its last
  parameter. The one without it stays.
- The extension hears it through a default method on `ExtensionWiringService`,
  `workflowFoundSuspended(SuspendedWorkflowFound, PC)`. No new registration exists on either platform.
  The core calls only the extensions which match the adapter, with the same filter as
  `startWorkflowProcessing`, and with the processing context of that adapter and module. A module or an
  adapter which the start did not deploy reaches nobody.
- The record `SuspendedWorkflowFound` names the adapter id, the module, the process (not scoped), the
  aggregate id, the BPMS' own id of the workflow, the task of the call, when the adapter found it, and
  the phase: `CALL` for a refused call, `WAITING` for a waiting outbox entry. It does not say who
  suspended the workflow or when. The adapter would need another request for that, and some BPMS do not
  know the time at all.
- The call is synchronous, on the caller's thread: the application's thread in phase one, the outbox's
  thread in phase two. The core catches every `RuntimeException` of an extension, logs a warning with
  the extension, the adapter id and the workflow id, and calls the next extension. The core's reporter
  catches once more, for a defect of the core itself. So the adapter throws afterwards exactly what it
  would have thrown without the report. An extension cannot make the application's call fail.
- No outbox. In phase one the application's transaction rolls back right after the check, and an entry
  written in it would go with it. An entry in a transaction of its own needs a store and a second
  transaction per refused call, for news which an extension's own check finds anyway. In phase two the
  waiting entry is in the outbox already. A crash between the report and the hand-off loses the news.
  That is accepted.
- An extension must not write in the caller's transaction, must not call the BPMS, and must return at
  once. It hands the work to a thread of its own. The javadoc of `workflowFoundSuspended` says so.
- The adapter reports only where it really found a suspension, just before it throws, not in a
  `finally`. Phase two reports on every attempt, and the extension filters out the repetitions. Signals
  and messages sent to a suspended workflow are not reported, because no adapter refuses them.
- The core's reporter, `SuspendedWorkflowReporting`, is an object of its own, because the adapters are
  built before the deployment service which knows the extensions. Each start connects its deployment
  service to it. A report before that is dropped.

**Rejected.** A separate listener interface for extensions: a cleaner name, but new registration code
on both platforms and a second copy of the type matching. An executor of the core's own: it would stop a
slow extension from holding the caller, but adds a thread pool for one event and makes every test
asynchronous. It is worth it only once more runtime events follow.

**Tests.** `DeploymentServiceTest$SuspendedWorkflowTests` holds the filter, the isolation of an
exception and the report before the connection. `AdapterCollaboratorsTest`,
`AdapterBeanRegistrarSupportTest` and `AdapterCollaboratorsSupportTest` hold the reporter in the
collaborators. `SuspendedWorkflowReachesExtensionsTest` (Spring Boot) and
`DeploymentPipelineTest#aSuspendedWorkflowReachesTheMatchingExtensions` (Quarkus) hold it in a booted
application with the BPMS double.
