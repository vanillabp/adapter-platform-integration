### A BPMN process belongs to exactly one workflow aggregate

Proposed by story 952 after a finding about decision 124. Decided by the maintainer on 2026-10-10 ("stop the
start"). Number 125 is reserved for it.

Within one workflow module, a BPMN process id may be declared only by `@WorkflowService` classes of one workflow
aggregate. Where classes of different aggregates declare the same id, the start ends. This holds for every way of
declaring it: one class names it as its `bpmnProcess` and another lists it in `secondaryBpmnProcesses`, both name
it as their `bpmnProcess`, or both list it in `secondaryBpmnProcesses`. Classes of one aggregate may still share a
process, and their handlers are merged as before. The same id in another workflow module is another process.

**Why it ends the start.** Until now the registry of task handlers logged a warning and kept the class it found
first. That was the behaviour of version 1. Which class comes first is the order of the class scan, and since
decision 124 that order decides more than which handlers run:

- The class which starts the process comes first: the process is a workflow of its own. The handlers of the other
  class are ignored without a word, and a call activity in the other workflow starts the process with the wrong
  aggregate.
- The class which lists the process as secondary comes first: the process counts as a called one. It gets no start
  and no end of its own, and its tasks load the aggregate of the caller. `ProcessService.startWorkflow` of the
  other aggregate still starts it, under the id of an aggregate its tasks never load.

A behaviour which changes with the order of the class scan cannot be kept, even where version 1 kept it. Version 1
had no `@WorkflowEnded` and no `@WorkflowStartedByBpms`, so the order cost it less.

**Where it is checked.** As early as each platform can:

- Quarkus, while the application is built, in `ProcessServiceBuildStepProcessor`.
- Spring Boot, while the first `ProcessService` is built. That is the first moment the workflow module of every
  class is known, and it is before any handler is registered. The check in `ProcessServiceBeanRegistrar` at
  definition time sees no workflow modules yet.
- `WorkflowTaskRegistry#registerWorkflowService` throws as well, for a platform integration which does not check.

All three use `AProcessBelongsToOneAggregate`, so the text is the same everywhere. It names both classes, both
aggregates and how each declares the process. Then it gives advice for the case:

- To make the process a workflow of its own, remove it from `secondaryBpmnProcesses` of the other class. A call
  activity may still call it, but then the call is a matter of the BPMS: the mappings of the call activity in the
  BPMS set up the data the called workflow gets, not VanillaBP. The text does not say "process variables",
  because not every BPMS has them. Two separate workflows are usually better started and synchronised by
  messages, so the contract between them lives in business code and not in the BPMN.
- To make the process a step of the other workflow, only the class of that workflow lists it as secondary.
- Where two workflows list it as secondary, it can be a step of one of them only. The other gets a copy with an
  id of its own, or the process becomes a workflow of its own.

**Version 1** logged a warning and went on. An application which relied on that has to decide what the process
is. `UPGRADE.md` and the wiki page "Migrating from version 1" say so.

`AProcessBelongsToOneAggregateTest` of `migration-adapter/runtime` holds the text and the registry in both orders.
`AProcessBelongsToOneAggregateTest` of the Spring Boot main integration test and the `AProcessOfTwoAggregates*Test`
classes of the Quarkus deployment module hold the start of a real application, in both orders. On both platforms,
classes of one aggregate sharing a process still start.
