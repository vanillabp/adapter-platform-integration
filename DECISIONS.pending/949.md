### 124. A called process is not a workflow of its own, so its start and its end stay inside the workflow

Proposed by story 949 after analysis 948. Decided by the maintainer on 2026-10-09 ("only the one at the top").
Extends decision 123.

A process called by a call activity runs on the workflow aggregate of the process which called it. So it is a step
of that workflow, and not a workflow of its own. `@WorkflowStartedByBpms`, `@WorkflowEnded` and the start row of the
delivery log belong to the process the aggregate was started with. The start and the end of a called process do not
reach the application.

**Which process is a called one.** The core decides it, because only the core reads the annotations. A process is a
called process when the application declares it only in `secondaryBpmnProcesses`, never as a `bpmnProcess`, and an
adapter deployed a model for it during this boot. The second half is what keeps renamed processes working. The id a
renamed process left behind is declared as a secondary process as well, but no model arrives for it any more. The
BPMS still holds workflows under that id, and they were started under it. For them, that id is the process at the
top, so they keep their start and their end. Decision 34 describes such ids.

**What the core does.**

- `WorkflowEndedInvoker#workflowEndedHandlerExists` answers `false` for a called process, so an adapter attaches no
  end listener there.
- `BpmsInitiatedStartInvoker#startsAWorkflowOfItsOwn` is new and answers `false` for a called process. Its default
  answers `true`, so an adapter written before it keeps compiling.
- A notification which still arrives for a called process, from a model deployed before this rule, is answered
  without effect on the workflow. An end only reports the open tasks of that instance as canceled. It calls no
  `@WorkflowEnded` method, leaves the election hint alone and releases nothing. A start builds no aggregate and
  writes no start row. It answers with the id the instance already carries, and it is refused where the instance
  carries none.
- A called process with a start event the BPMS fires by itself (timer, signal, condition) ends the deployment.
  Nothing would build the aggregate of the instance such a start event creates.
- The end of the workflow at the top releases the delivery records under every BPMN process id the workflow service
  serves. Until now the end of the called process released its own records. That end is no longer reported, so
  without this the records of a called process would wait for the retention.
- `workflowIdOf` and `workflowStartOf` read the start row under every served id, as before. Where no start row
  exists, they fall back on the open tasks of the reader's own process only. An open task of a called process names
  the instance of the called process, and that is not the workflow of the aggregate.

**Why the adapters ask instead of the core ignoring the notification.** A listener costs the model something, and
on Camunda 8 a start listener holds the instance until a worker answers its job. A core which only ignored the
notification would leave that cost in place for nothing. The runtime guard in the core is there for the models
deployed before.

**Version 1** had no `@WorkflowEnded` and no `@WorkflowStartedByBpms`, so no version-1 application sees a
difference.

`ACalledProcessIsNoWorkflowTest` on both platforms holds the rule: no start and no end listener for the called
process, one `@WorkflowEnded` per workflow, the renamed id keeps its end, the records go with the workflow at the
top, and the start of a called process builds nothing. `OpenUserTasksOfAnAggregateTest#withoutAStartRowACalledProcessNamesNoWorkflow`
holds the fallback.
