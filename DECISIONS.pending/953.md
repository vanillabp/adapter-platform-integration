### The version a start deployed needs a method for every one of its tasks

Proposed by story 953 after a measurement on Camunda 7. Decided by the maintainer on 2026-10-10 ("stop the start",
no exception for a rolling deployment). Number 126 is reserved for it. It builds on decisions 15, 60 and 67.

Every task of the model a start deploys needs a `@WorkflowTask` method whose version range covers the version the
BPMS gave that model. Where no method of a task covers it, the start ends. The message names the task, the version,
the BPMN process, the workflow module, the adapter and the methods with their ranges. It suggests three fixes: widen
the range (e.g. `version = ">=1"`), add a method for that version, or deploy the model the method serves.

**Why it ends the start.** The wiring validation asks for a method for every task, but it runs before the
deployment. At that point the version is not known, so it ignores the ranges. A delivery picks the method by
version. So a task whose only method serves `>1`, in a model the BPMS keeps as version 1, passed the start and
failed at every delivery. Measured on Camunda 7 with the `bpmn-versioning` blueprint: the start logged one warning,
and every workflow stopped at that task, three attempts and then an incident. Camunda 8 has the same shape, because
the rule lives in the core. Decision 67 asks that a delivery finds what the start accepted. This case broke that
rule through the version.

**Where it is checked.** In the check of the deployed versions (decision 15), because that is the first moment the
version is known. The tasks are the ones the adapter handed to the wiring validation, so no model is read again,
and a BPMS whose catalog cannot read a model is checked as well. Each adapter is held against the version its own
BPMS gave the model.

**What it does not change.**

- A method which serves no version the BPMS holds stays a warning, as decision 60 says. That finding is about a
  method without a task. This one is about a task of the deployed model without a method.
- A task without any method passed the wiring validation only through `implemented-externally`, so it is somebody
  else's and is not asked about.
- A process nobody claims has no methods to check. A called process is checked against its own version, as its
  deliveries are (decision 123). A process without tasks has nothing to check.
- The older versions a BPMS holds keep their warnings and errors. A version the configuration fades out is not
  touched, and fading out the deployed version still ends the start with its own message.
- A BPMS which reports no deployed version is not asked.

**No exception for a rolling deployment.** While another node deploys a newer model, this node may start on the
older one. The version this node deployed is the one it starts on, and the workflows it starts run on that version.
So the rule holds there too.
